# Model the database

## Inputs

`docs/04-uml/classes.md` (if it exists), `docs/03-casos-de-uso.md`, `docs/02-requisitos.md` (performance and privacy RNFs) and the stack in `AGENTS.md`.

## Procedure

1. **Entities and relationships.** Derive them from the domain model. Normalize up to 3NF; denormalize only with a recorded reason (report performance, for example).
2. **ER diagram** (`erDiagram`): entity names in UPPER_CASE_WITH_UNDERSCORES, attributes with type and `PK`, `FK`, `UK` markers.
3. **Data dictionary:** one table per entity with column, type in the chosen DBMS, nullability, default, constraints and description.
4. **Conventions:** primary key `id` (UUID or bigint, depending on the stack), `created_at`/`updated_at` in UTC, soft delete (`deleted_at`) when there is history, money values in `numeric(12,2)` or integer cents.
5. **Indexes:** for each frequent query of the use cases (filtered lists, searches, joins), record the index and the UC that justifies it.
6. **Reference DDL** consistent with the diagram. The official migrations stay in the code (generated by the ORM or written in SQL).
7. **Volume and critical queries:** estimate rows and growth per table; for each critical query, the time target and the source UC/RNF. Large tables purged by date: evaluate partitioning (ADR).
8. **Loads and integrations:** source, frequency, deduplication key (idempotent load) and destination of rejected records.
9. **Roles:** application without DDL, migrations with DDL only at deploy, reports read-only (preferably through views).
10. **Privacy (LGPD/GDPR):** list every personal data item with purpose, legal basis, retention and protection (hash, encryption, masking). Sensitive data (health, biometrics, etc.) needs special attention: flag it to the user.
11. **Migrations and backup:** tool, how to apply, rollback, expand → migrate → contract for incompatible changes, seeds, backup with RPO/RTO and restore test.

## Output

`{{prumo}} validar` with no errors; summary with the number of tables, personal data identified and decisions that deserve an ADR (for example, multi-tenant by schema or by column).
