## Golden rule: the specification comes first

1. The documents in `docs/` are the source of truth for what must be built. Read them before proposing or changing code.
2. Before implementing a story, walk the full trail: **HU → UC → RF/RNF/RN → screens (TL) → data model → ADRs**.
3. If the code needs to diverge from the specification, **stop and point out the divergence** to the user. Do not silently adjust the specification to fit the code.
4. **Approved documents are read-only** (list in `projeto.prumo.json` → `aprovados`). Change requests become a change record: `{{prumo}} mudanca "title"`.
5. **Do not invent requirements.** Business questions become questions in section 9 of `docs/00-briefing.md`.
6. Blocks between `<!-- prumo:gerado:... -->` and `<!-- prumo:gerado:fim -->` came from the form (`especificacao.prumo.json`) and are the user's decisions: complete what is missing around them, without rewriting or contradicting them. The form's RF/RN/UC IDs also apply in the documents.
7. `[FILL: ...]` blocks are gaps. When filling in a document, replace all of them or state why they stayed open.

## Adverse situations (what to do without improvising)

- **Vague or contradictory briefing:** do not pick a side. Record both versions as a question (section 9 of the briefing) and continue only with what does not depend on it.
- **Client changes the scope midway:** no code before the record `{{prumo}} mudanca "title"` with its impact on deadline and price.
- **Stack outside the profile:** record the choice in an ADR (`{{prumo}} adr "title"`) and write the conventions in `docs/07-arquitetura.md` before coding; do not apply another stack's conventions.
- **Missing tool** (git, node, php, database...): do not install anything globally or change the stack on your own; tell the user what is missing and the command to install it.
- **Real client data** (tax IDs, cards, passwords, tokens): never in `docs/`, code or commits. Use fake data; secrets only in `.env`.
- **A hook blocked:** read the reason and fix the cause. Do not bypass the guard another way (shell, another file).

## After every significant change

Significant change = 3 or more code files, 80 or more lines, or any change to authentication/authorization, database (migrations, models), routes/API, dependencies, infrastructure (Docker, CI/CD), configuration or sensitive data. When you finish a change like that, **before ending**:

1. **Update the affected documentation** following `.claude/skills/atualizar-documentacao/SKILL.md`.
2. **Look for security flaws** following `.claude/skills/revisar-seguranca/SKILL.md` (includes `{{prumo}} seguranca`) and record the findings in `docs/12-seguranca.md`.

In Claude Code a hook enforces these two steps; in other agents, follow this rule on your own.

## Writing the documents

- **One fact, one place.** Business terms are defined once in the glossary of `docs/02-requisitos.md`; each ID, in its owner document. Elsewhere, cite the ID instead of repeating the text.
- **Structure before prose:** tables and lists; paragraphs of up to 3 sentences; sentences of up to 40 words.
- **Verifiable:** numbers, names and criteria. A vague term ("fast", "intuitive", "modern") becomes a metric or a P-xx question.
- **No filler:** no introductions that repeat the title, "it is worth noting", "in order to" (use "to").
- **Instructions in the imperative**, one action per item. A section that does not apply: "Not applicable: reason", in one line.
- `{{prumo}} validar` reports the excesses as style warnings.

## Token economy (without losing quality)

- **Load only the trail you need:** `{{prumo}} contexto HU-003` (or UC-xxx, RF-xxx...) prints only the blocks linked to that item. Prefer it to reading whole documents; to find something specific, search by ID (`Grep "UC-004" docs/`).
- **Do not reread** what is already in context; read large files in parts.
- **Edit precisely:** use targeted edits instead of rewriting whole files.
- **Delegate long explorations** (scanning the code, reviewing many files) to subagents, which return only the conclusion.
- **Do not read** dependencies, builds, lockfiles or minified files (`node_modules/`, `dist/`, `*.lock`, `*.min.js`).
- **Short final answers:** what changed, pending items and decisions. Do not repeat the content of the files.
- Quality comes first: if context is missing to decide well, read what you need.

## Definition of done

- Implementation faithful to the documents and to the story's acceptance criteria.
- Automated tests covering the acceptance criteria; suite passing.
- Affected documentation updated (skill `atualizar-documentacao`) and security review done (skill `revisar-seguranca`).
- `{{prumo}} validar` with no errors and `{{prumo}} rastreabilidade` regenerated.
- Story status updated in `docs/08-backlog.md`.

## Security

- Never read, display or commit `.env`, private keys or credentials. Document the variables in `.env.example`.
- Do not run destructive commands (`rm -rf`, `git push --force`, `git reset --hard`, `DROP`, database resets) without an explicit request from the user.
- Personal data follows the privacy section of `docs/06-banco-de-dados.md` (privacy law: LGPD, GDPR or the one that applies).
